# Q36 / QuarkStar on the BC250

On September 28, 2026, **Qwen3.6-35B-A3B ran fully resident through Q36 at 71.90 generated tokens/sec at 2K context, 70.09 at 4K and 64.09 at 8K**, averaged across three sweeps. It passed all three isolated SSH repair cases, but needed retries after tool-argument type errors.

This is a separate engine and model from [Qwen3-Coder-Next](coder-next.md). No SSD expert streaming was used. The production API remains llama.cpp with Qwen3.5-9B and HauhauCS Aggressive; Q36 is staged as an evaluated candidate.

## Model and runtime

- [Ninnix/q36](https://github.com/Ninnix/q36), commit `1305843c735380f912619548b121cba8601f2f85`, built with `make vulkan-bc250 -j4`.
- [Qwen3.6-35B-A3B mixed Q2 weights](https://huggingface.co/Ninnix96/Qwen3.6-35B-A3B-gguf), revision `29e6b31044134d6b2370b25032d090f7eb5a95dd`.
- File: `Qwen3.6-35B-A3B-AntirezExperts-IQ2XXS-gateup-Q2K-down-Q8rest.gguf`, **11,737,316,384 bytes**, SHA-256 verified. [Manifest](../benchmarks/q36/model-manifest.json).
- Routed gate/up experts use IQ2_XXS; routed down experts use Q2_K; other components retain higher precision. This is not uniform two-bit quantization of every tensor.
- Existing Ubuntu 24.04.5, kernel 6.8.0-142-generic and RADV 25.2.8; eight CPU cores, sixteen threads and forty routed CUs.
- Runtime confirmed the **BC250 fast path**, subgroup 64 and graphics fallback queue. No ACE kernel/Mesa patches were installed.
- No CPU/GPU clock or voltage changes, GPU governor, speculative MTP, vision projector or additional firmware flash for this evaluation.

The default shader wrapper uses glslangValidator. Installed glslang 15.1 and shaderc 2023.8 both rejected `GL_EXT_integer_dot_product`. An isolated official **glslang 16.6.0** release, verified against its GitHub asset digest, built successfully. A private PATH shim exposes that binary as glslangValidator without replacing the system compiler. `make test` passed. [Compiler manifest](../benchmarks/q36/compiler-manifest.json).

## Memory configuration changed

The initial 8/8 split was replaced with a **512 MiB UMA reservation**. Linux now reports `MemTotal: 15573720 kB`, about **14.85 GiB**, and Vulkan reports 14.90 GiB UMA. Kernel parameters follow [Q36's BC250 guide](https://github.com/Ninnix/q36/blob/1305843c735380f912619548b121cba8601f2f85/BC250.md):

```text
amdgpu.gttsize=14750 ttm.pages_limit=3959290 ttm.page_pool_size=3959290
```

After reboot, both TTM values read back as 3959290; the CPU remained 8/16, register readback confirmed 40/40 routed CUs, and the original API started successfully. These settings expand GPU access to the shared memory pool; they do not add physical memory. The appropriate parameters can vary with kernel version.

The previous GRUB configuration and CMOS readings were backed up. A local rollback script sets `UMA_SIZE` back to 8192, removes the dedicated GRUB drop-in and regenerates GRUB; a reboot applies the rollback. The new layout was retained after the evaluation.

Re-running the original Qwen3.5-9B Q4_K_M benchmark under this layout produced **316.92 prompt tok/s and 52.36 generation tok/s**, versus the earlier 316.97 / 52.17 at 8/8. That short comparison shows no material throughput change for the existing model; it does not establish equivalence for all workloads. [New-layout baseline](../benchmarks/q36/qwen35-new-memory.json).

## Resident speed measurements

| Context frontier | New prefill tokens at this frontier | Mean prefill tok/s | Mean generation tok/s | Generation samples |
|---|---:|---:|---:|---|
| 2048 | 2048 | 526.53 | **71.90** | 69.84, 72.80, 73.07 |
| 4096 | 2048 | 426.82 | **70.09** | 69.91, 70.01, 70.35 |
| 8192 | 4096 | 316.53 | **64.09** | 63.99, 64.01, 64.26 |

Three separate q36-bench processes each swept the same upstream story prompt through 2K, 4K and 8K. Each frontier generated exactly 128 tokens using greedy decoding with EOS ignored. The context allocation was 8321, six helper threads, prefill chunk 1024, Q8_0 K cache and Q4_0 V cache.

**Prefill is incremental:** the 8K row measures adding 4096 tokens to the existing prefix, not processing a fresh 8192-token prompt. This differs from llama-bench's synthetic, separate prompt/generation tests, so do not calculate an engine-only speedup from the Q36 and Qwen3.5 tables. Models, quantization, context and workloads differ.

The test service had a 14 GiB host cgroup cap, no cgroup swap and a 180-second timeout per sweep. All three sweeps and the baseline completed successfully. Sampled peak GPU edge temperature across the complete Q36-plus-baseline sequence was **67°C** (the interim Q36 reading was 66°C). Captured cgroup counters showed no memory-limit events or OOM kills. Host cgroup accounting is not a complete measurement of GPU memory. No GPU-reset/fault or OOM messages were found in the checked boot log after testing.

## Consecutive requests and cache behavior

The same short workload used for Coder-Next was sent to one persistent Q36 server: three identical palindrome requests, then a three-turn word-frequency conversation. Each response was forced to 32 tokens with temperature zero, seed 42, `ignore_eos=true` and `think=false`. Context was 4096 with one resident session. The fixed limit truncates code; this is a timing experiment, not a code-correctness test.

| Request | Default server generation tok/s | Default total latency | Disk-KV generation tok/s | Disk-KV total latency |
|---|---:|---:|---:|---:|
| Identical 1 | 76.76 | 0.640 s | 77.20 | 0.894 s |
| Identical 2 | 78.71 | 0.587 s | 79.81 | 0.764 s |
| Identical 3 | 78.73 | 0.588 s | 79.67 | 0.625 s |
| Conversation 1 | 77.95 | 0.584 s | 78.99 | 0.826 s |
| Conversation 2 | 77.73 | 0.690 s | 78.45 | 0.819 s |
| Conversation 3 | 77.39 | 0.956 s | 78.63 | 0.924 s |

The default server reported **zero cached prompt tokens in all six requests**. Do not attribute its small speed changes to prompt-cache reuse. A separate server run enabled disk KV with a 512 MiB budget, minimum 16 tokens, zero boundary trim and 16-token alignment, intentionally lowering thresholds for these tiny prompts. Requests 2/3 in each group then reused **32 tokens**. Save/load overhead meant it was not consistently faster end-to-end.

Generation rates come from Q36's final per-request decoding log, which rounds to two decimals. The API does not return llama.cpp's `timings` object. Wall-clock latency includes the whole request and is measured separately. These log rates use Q36's accounting and are not interchangeable with llama.cpp's rate convention.

[Default-server request results](../benchmarks/q36/consecutive-no-disk-kv.json) · [Disk-KV request results](../benchmarks/q36/consecutive-disk-kv.json). Startup and model loading are excluded from request latency. Caches were not explicitly flushed, and only one six-request sequence was run per configuration.

## Isolated SSH agent evaluation

The existing restricted SSH fixture was reused, with the same five tools, 12-turn budget, temperature zero and 384-token response limit. Q36 used non-thinking mode and 4K context. Its API listened on loopback and was reached through a separate SSH tunnel; the model's tool identity remained restricted to the lab service. The general Q36 coding agent was not given administrator access.

| Fault | Full pass | Time | Tool calls | Tool errors |
|---|---|---:|---:|---:|
| Invalid port | Yes | 22.08 s | 10 | 3 |
| Stale message | Yes | 16.62 s | 10 | 3 |
| Invalid bind address | Yes | 24.97 s | 12 | 5 |

All cases recovered, verified systemd status and HTTP health, and produced a final report. The repeated errors were `write_config` receiving a JSON object where the declared schema required a JSON string. The controller rejected those calls, and the model/runtime eventually produced accepted arguments. **3/3 completion does not mean error-free tool integration.**

[Case summaries](../benchmarks/q36/agent-summary.json). This is one run per case on a small private fixture, not a broad coding/security evaluation. Raw lab transcripts and SSH credentials are not published. Q36 has not been run through the separate static security-review fixture or a larger coding-quality suite.

## Reproduction

Build the pinned checkout using glslang 16.6.0 or another compiler that supports its shaders. Verify the model manifest, memory settings and GPU routing first. Run one large inference process at a time.

```bash
make vulkan-bc250 -j4
make test -j4

# Repeat this sweep three times, using a distinct CSV filename each time.
./q36-bench --vulkan -m /path/to/verified-model.gguf \
  --prompt-file tests/long_context_story_prompt.txt \
  --ctx-start 2048 --ctx-max 8192 --step-mul 2 --ctx-alloc 8321 \
  --gen-tokens 128 --cache-type-k q8_0 --cache-type-v q4_0 \
  --threads 6 --csv resident-1.csv

# Persistent server for the short API tests; loopback only.
./q36-server --vulkan -m /path/to/verified-model.gguf \
  --host 127.0.0.1 --port 18083 --ctx 4096 --batched-session 1 \
  --threads 6 --cache-type-k q8_0 --cache-type-v q4_0 2> q36-server.log

# Run from this build-guide repository in another terminal.
python3 scripts/q36-consecutive-prompts.py \
  --base-url http://127.0.0.1:18083 --model qwen3.6-35b-a3b \
  --server-log /path/to/q36-server.log --output q36-consecutive-results.json
```

The story-prompt source and SHA-256 are recorded in metadata. For the disk-KV variant, add `--kv-disk-dir /path/to/test-cache --kv-disk-space-mb 512 --kv-cache-min-tokens 16 --kv-cache-boundary-trim-tokens 0 --kv-cache-boundary-align-tokens 16`. This short-prompt cache configuration is an experiment, not a recommended production default.

Temporary test services were removed afterward and the isolated lab was stopped. Source, binaries, weights and evidence remain staged. The original authenticated API was restored; Q36 was not installed as its replacement. Longer thermal testing, broader agent cases and a quality comparison remain future work.
